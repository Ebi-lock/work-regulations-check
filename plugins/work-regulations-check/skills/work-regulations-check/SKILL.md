# 就業規則チェック

日本の就業規則・関連規程を、労働基準法をはじめとする労働関係法令に照らして点検する。

**このファイル中の `scripts/…` と `references/…` は、すべてこのスキルのディレクトリからの相対パス。**
スキル読み込み時に示されるベースディレクトリを基点に実行すること
（例: `python3 <ベースディレクトリ>/scripts/extract_text.py …`）。
作業ディレクトリはユーザーのプロジェクトであってスキルの置き場所ではないので、
相対パスのまま実行すると「ファイルが見つかりません」になる。

## このスキルの位置づけ

出力は **社労士・弁護士に相談する前の一次スクリーニング** であり、法的助言ではない。
これはレポートの品質を下げる言い訳ではなく、書き方を決める前提である。読み手（多くは人事担当者）が
専門家に持ち込んだときにそのまま議論の材料になるよう、**必ず「該当条文の引用」と「根拠法令の条番号」をセットで示す**。
根拠を示せない指摘は、指摘しないほうがよい。

判断に迷ったら、断定せずに「要確認」として理由と確認先を書く。人事の実務では、
誤った断定（本当は適法な規定を「違法」と書く）のほうが、見落としよりも高くつくことがある。

## 全体の流れ

1. テキストを抽出する
2. 条文のインデックスを作る
3. 4つの観点でチェックする
4. 根拠を原典から引く
5. レポートを書く

**根拠は記憶で書かない。** 条番号・割増率・日数・人数要件は、記憶で書くとずれる。
原典は次の順で当たる。

```
厚労省の改正情報 → e-Gov で現行法を確認 → 施行日を確認 → 就業規則への影響を判定
```

| 何を | どこから | 使うもの |
|---|---|---|
| 何がいつから変わるか | 厚労省 国会提出法案の概要 | `scripts/mhlw_bills.py` |
| 条文の原文 | e-Gov法令検索 | `scripts/fetch_law.py` |
| 施行日・未施行の有無 | e-Gov法令検索 | `scripts/fetch_law.py --status` / `--asof` |
| 修正案の条文 | 厚労省 モデル就業規則 | `scripts/model_rules.py` |

詳しくは `references/amendments.md`（法改正の流れ）と `references/sources.md`（引用の作法）。

## 1. テキストを抽出する

```bash
python3 scripts/extract_text.py <ファイルパス> -o /tmp/rules.txt
```

対応形式と挙動:

| 形式 | 方法 |
|---|---|
| `.docx` | python-docx。本文＋表＋ヘッダーフッターを抽出する |
| `.doc` / `.rtf` / `.odt` | macOS の `textutil` |
| `.txt` / `.md` | そのまま |
| `.pdf` | `pypdf` があれば使う。無ければスクリプトがその旨を出力するので、**Read ツールでPDFを直接読む**（`pages` 引数で20ページずつ） |

PDF を Read ツールで読む場合は、条文の抜けが命取りになるので **全ページを通しで読む**。
「重要そうなところだけ」拾うと、必須記載事項の漏れを見逃す。

抽出後、冒頭・末尾・途中を目視して、文字化けや段組みの崩れで条文が壊れていないか確認する。
壊れていたら、その旨をユーザーに伝えて元ファイルの提供方法を相談する（崩れたテキストへの指摘は無意味なので、
ここで止まる判断は正しい）。

## 2. 条文のインデックスを作る

```bash
python3 scripts/check_structure.py /tmp/rules.txt
```

このスクリプトは機械的に判定できるものだけを扱う。出力は形式チェックの結果であると同時に、
**この規程に何条まであり、どの章に何が入っているか** の地図になる。以降のチェックで
「○○に関する定めが見当たらない」と書く前に、必ずこの地図で探し直すこと。

検出するもの:
- 条番号の飛び・重複・逆順（漢数字・算用数字の両方に対応）
- 内部参照の参照先が存在しないもの
- **存在しない項への参照**（「第67条第3項」だが第67条は第2項までしかない、など）
- **内部参照の解決先の一覧** ― 参照元の文と、参照先の条見出しを並べて出す
- 外部法令への参照（「労働安全衛生法第66条の8」など）。内部参照とは区別して出る
- 別規程・別表への参照（「○○規程の定めによる」）の一覧 ― 添付されていない規程は指摘対象
- 用語のゆれ（従業員／社員／労働者 など）

### 参照の解決先は必ず目で読むこと

**条番号は合っているが中身が違う参照は、機械では判定できない。**
「第51条に基づき割増賃金を支払う」と書いてあり第51条が実在していても、その第51条が
「社員紹介奨励手当」なら誤りだが、存在チェックは通ってしまう。

この種の誤りは規程の改定を重ねた規程で頻繁に起きる（条を挿入したときに参照側を直し忘れる）。
スクリプトは参照元と参照先の見出しを並べて出すので、**そこを読んで文意が噛み合うか確かめる。**
件数が多ければ `--refs` で全件出す。

```bash
python3 <ベース>/scripts/check_structure.py /tmp/rules.txt --refs
```

スクリプトは網羅的ではない。出力を読んだうえで、目視でも見出しと本文のずれ、
条見出しと中身の不一致、削除条文の残骸（「第○条 削除」の扱い）を確認する。

## 3. 4つの観点でチェックする

各観点の判断基準は references/ にある。**チェックを始める前に3つとも読むこと。**
記憶だけで条文番号や割増率を書くと数字を間違える。

| 観点 | 参照ファイル |
|---|---|
| 必須記載事項の漏れ | `references/required-items.md` |
| 違法・リスクのある条項 | `references/risk-clauses.md` |
| 法改正への未対応 | `references/amendments.md`（4ステップの流れ） |
| 根拠条文の引き方・出典 | `references/sources.md` |

法改正の確認は、`references/amendments.md` に書いた次の順で行う。**順番に意味がある。**

```
厚労省の改正情報          何が、なぜ変わるのか。改正の全体像と施行期日の考え方
        ↓                 scripts/mhlw_bills.py --summary <国会回次>
e-Gov で現行法を確認      条文が実際にどう書かれているか。引用できる原文
        ↓                 scripts/fetch_law.py <法令> <条番号>
施行日を確認              いま効いているのか、これから効くのか
        ↓                 scripts/fetch_law.py <法令> --status / --asof
就業規則への影響を判定    その規程のどの条を、どう直す必要があるのか
```

e-Gov から始めると「いまの条文」しか分からず、何が新しいのかも、なぜ入ったのかも見えない。
厚労省の資料だけで書くと、条文の原文が手に入らず引用が不正確になる。両方を、この順で使う。

`references/amendments.md` には基準日時点の改正一覧も載せてあるが、**表を信じきらないこと。**
基準日より後にチェックするなら `python3 scripts/mhlw_bills.py --recent 3` で
直近の国会提出法案を拾い、表に無い改正が出ていないか確認してから始める。

### チェックするときの姿勢

- **事業所の規模・業種で結論が変わる項目がある。** 常時10人以上か、中小企業かどうかで
  義務の有無が変わるものは、前提が不明なら両方のケースを書くか、ユーザーに聞く。
- **「書いていない」ことの意味を区別する。** 絶対的必要記載事項の欠落は法違反。
  相対的必要記載事項は「制度があるのに書いていない」場合のみ問題で、制度自体が無ければ問題ない。
  後者を一律に「漏れ」と書くと、レポートが指摘だらけになって本当に危ない箇所が埋もれる。
- **数を絞る。** 30件の指摘より、重大な5件と軽微なものの一覧のほうが実務では動かしやすい。

## 4. 根拠を原典から引く

指摘の一覧ができたら、**書こうとしている根拠をひととおり原典で確認する。**
条番号・割増率・日数・人数要件は、記憶で書くとかなりの確率でずれる。

### 法改正に関する指摘

`references/amendments.md` の4ステップに従う。起点は厚労省。

```bash
python3 scripts/mhlw_bills.py --recent 3          # 直近の国会提出法案
python3 scripts/mhlw_bills.py --summary 217       # 概要PDF（改正内容と施行期日）
python3 scripts/fetch_law.py 労施法 33            # 条文の原文
python3 scripts/fetch_law.py 労施法 --status      # 施行日と未施行の改正
python3 scripts/fetch_law.py 労施法 33 --asof 2026-10-01   # 未施行の改正を先読み
```

概要には「義務付け」「努力義務」「責務」の区別と施行期日が書かれている。
ここを読み違えると、努力義務を「違反」と書くことになる。

施行済みか未施行かで指摘の書き方を変える。施行済みで対応が無ければ要是正、
未施行なら要検討として「○年○月○日から義務化されるため次回改定で織り込む必要がある」と書く。
**未施行のものを「違反」と書かない。**

### 現行法に関する指摘

```bash
python3 scripts/fetch_law.py 労基法 89 91 37      # 条文を取得
python3 scripts/fetch_law.py 育介法 --grep 看護   # どの条にあるか分からないとき
python3 scripts/fetch_law.py --list               # 引ける法令の一覧
```

出力の先頭に現在の版の施行日が出る。古い条文を引いていないか確認する。

### 修正案

自分で条文をひねり出すより、厚労省の規程例に合わせる。

```bash
python3 scripts/model_rules.py --grep 年次有給休暇      # 規程例（両方から検索）
python3 scripts/model_rules.py --grep 出生時育児休業     # 育介法まわりは ikuji が当たる
python3 scripts/model_rules.py --grep 懲戒 --explain    # 規程例＋厚労省の解説
python3 scripts/model_rules.py --toc                    # 目次
```

引ける規程例は2つある。

| 名前 | 内容 |
|---|---|
| `model` モデル就業規則 | 就業規則の本体 |
| `ikuji` 育児・介護休業等に関する規則の規定例 | **育介法まわり** |

**産後パパ育休・子の看護等休暇・柔軟な働き方の措置などはモデル就業規則に入っていない。**
育介法は改正が最も激しく指摘が集中する領域なので、育児・介護関係の条文案を書くときは
必ず `ikuji` 側を引く。ケース①②③のように選択肢が並んでいるので、
事業場の事情に合うものを選んで提示する。

厚労省の文言なら労基署への説明が通りやすく、担当者が社内で承認を取るときにも使いやすい。
ただし **モデル就業規則と違うこと自体は指摘の理由にならない**。指摘するのは、
法令に反しているか、法令が求める記載が無い場合だけ。

### 通達（解釈）

条文だけでは運用が決まらないことが多い。行政がどう解釈しているかは通達に出る。
`labor-law` MCP が使えるなら、そこから引く。

```
mcp__labor-law__search_mhlw_tsutatsu   厚労省法令等DBを通達検索（キーワードは2語まで）
mcp__labor-law__get_mhlw_tsutatsu      本文を取得（data_id を渡す）
mcp__labor-law__search_jaish_tsutatsu  安全衛生関係の通達（JAISH）
mcp__labor-law__get_law                条文取得。45法令のプリセット
```

MCP が無ければ `scripts/fetch_law.py` で条文だけ引き、通達を根拠にしたい指摘は
「要確認」に回す。告示・指針・判例も e-Gov にないので、WebSearch で出典を確認できなければ同じ扱い。
詳しくは `references/sources.md`。

## 5. レポートを書く

この構成で出力する。ファイルに保存するかどうかはユーザーに合わせるが、
長くなるので原則 `<元ファイル名>_チェック結果.md` として保存し、要点だけチャットで伝える。

```markdown
# 就業規則チェック結果

**対象**: <ファイル名>（<全○条 / ○章>、<最終改定日が読み取れれば記載>）
**チェック日**: <日付>
**前提**: <常時使用する労働者数・業種など、判断の前提にした情報。不明なら「不明」と書く>

## サマリー

| 重要度 | 件数 | 概要 |
|---|---|---|
| 要是正 | n | 法令違反の疑いがあり、放置すると無効・是正勧告のリスク |
| 要検討 | n | 直ちに違法ではないが、紛争時に不利になりうる |
| 要確認 | n | 前提情報が足りず判断できない |

最優先で対応すべき3点:
1. ...

## 要是正

### 1. <見出し>

**該当箇所**: 第○条（<条見出し>）
> <規程の原文を引用>

**問題**: <何が法令のどの要求に反するか>
**改正の内容**: <法改正がらみの場合のみ。厚労省の概要資料から、何がいつ義務化されたか>
**根拠**: 労働基準法第○条（○年○月○日施行の版で確認。e-Gov法令検索）
> <fetch_law.py の出力をそのまま引用。要約すると意味が変わるので貼り付ける>
**修正案**: <モデル就業規則の該当条に準拠する場合はその旨>
> <そのまま差し替えられる条文案>

（以下同じ形式で繰り返す）

## 要検討

（同じ形式）

## 要確認

| 項目 | 確認したいこと | 確認先 |
|---|---|---|

## 形式面の指摘

| 箇所 | 内容 |
|---|---|

## チェックした範囲

- 参照した改正情報: 厚生労働省 国会提出法案（第○回国会の概要資料）
- 参照した法令: e-Gov法令検索（<取得日>時点）。各条文の施行日は本文に記載
- 参照した規程例: 厚生労働省「モデル就業規則」<版>
- 今回見ていないもの: <賃金規程など別規程、36協定、労使協定、運用実態>

---
本レポートは法令との突き合わせによる一次確認であり、法的助言ではありません。
実際の改定にあたっては社会保険労務士・弁護士の確認を受けてください。
```

### 修正案の書き方

修正案は「〜を追加してください」ではなく、**そのまま貼れる条文**で書く。
人事担当者が次にやる作業は条文の差し替えなので、日本語の条文体（「〜するものとする」「〜しなければならない」）で、
周囲の条文の文体・用語に合わせて書く。既存規程が「従業員」を使っているなら、修正案でも「従業員」を使う。

### 別規程への委任がある場合

「賃金については賃金規程の定めによる」のように委任されている項目は、**委任先が無ければそれ自体が指摘対象**
（絶対的必要記載事項は、就業規則本体か別規程のどちらかに必ず必要）。
委任先が手元に無い場合は、「漏れ」と断定せず「賃金規程の確認が必要」として要確認に入れる。
